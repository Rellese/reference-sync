# ReferenceSync: как подготовить чистую папку и отправить обновление в Eagle

Инструкция от 19 сентября 2026 года. Подходит для Windows и macOS.

## Что я сделал при предыдущей сборке

1. Создал ветку `release/v1.2.0-preparation` с готовыми исправлениями.
2. Обновил README, историю изменений и документы о данных, проверке и выпуске.
3. Отключил автоматическое открытие панели разработчика в manifest.json.
4. Добавил корректные шрифты и их лицензии.
5. Добавил сборщик `scripts/prepare-release.mjs` и действие `prepare:release`
   в package.json. Он копирует разрешённые файлы в НОВУЮ папку внутри dist.
6. Проверил чистую папку браузерными тестами и подготовил ZIP для передачи.
   ZIP — это папка проекта для распаковки, а не установочный файл Eagle.

Из рабочей ветки ничего вручную не вырезалось. Макеты, тесты и история
остались в репозитории; в папку для упаковки они просто не копировались.

## Основной порядок: сборка из VS Code

### 1. Выберите актуальную версию проекта

1. Откройте VS Code → «Файл» → «Открыть папку» и выберите рабочий репозиторий
   reference-sync — папку с package.json, manifest.json и каталогом js.
2. Нажмите название ветки в левом нижнем углу. Выберите ветку с готовым
   проверенным кодом И сборщиком. Изначально это `release/v1.2.0-preparation`.
3. В разделе «Управление версиями» откройте меню «…» → «Получить» / Pull.
   Не переключайтесь с несохранёнными изменениями: сначала сохраните их
   и сделайте осмысленный коммит.
4. Убедитесь, что последние нужные исправления и логотип есть в этой ветке.
   Обновление одной ветки не обновляет другую автоматически.

Если исправления находятся в `fix/m1-t09z-selection`, а сборщик — в release:
сначала переключитесь на release, затем откройте палитру команд
(Ctrl+Shift+P на Windows / Cmd+Shift+P на macOS), выберите “Git: Merge Branch”
и укажите ветку исправлений. При конфликте не выбирайте все изменения одной
стороны вслепую: проверьте оба варианта. После объединения снова проверьте
плагин и сохраните результат в коммите.

### 2. Подготовьте логотип, версию и описание

- Новый логотип положите в РАБОЧИЙ проект: `assets/logo.png`.
  В manifest.json должно быть `"logo": "assets/logo.png"`.
  Откройте картинку в VS Code и проверьте, что это настоящий PNG.
- Для следующего выпуска увеличьте version в manifest.json и package.json
  до одного и того же значения. Например, после 1.2.0 — 1.2.1.
  Самостоятельно менять id плагина нельзя: иначе Eagle воспримет его
  как другой плагин. Текст версии в интерфейсе также должен совпадать;
  если он задан отдельно в коде, обновите его при подготовке выпуска.
- В manifest.json должны оставаться `"devTools": false` и
  `"main": { "devTools": false, ... }`. Здесь многоточие означает остальные
  существующие поля: не вставляйте многоточие в сам JSON.
- Обновите CHANGELOG.md: перечислите изменения именно этого выпуска.
- Проверьте README.md, docs/PRIVACY.md, docs/REVIEW.md, docs/RELEASE.md.
  Они должны соответствовать текущему поведению и реальным проверкам.
- Сохраните всё и сделайте коммит. В «Управлении версиями» проверьте список
  изменений, добавьте нужные файлы, введите описание и нажмите «Commit».
  Затем «Синхронизировать изменения», чтобы сохранить коммит на GitHub.

Важно: сборщик берёт список файлов из Git, но содержимое читает из рабочей
папки. Поэтому перед сборкой рабочая папка должна быть чистой: без
незакоммиченных изменений. Новый файл, который ещё не добавлен в Git,
сборщик не возьмёт. Несохранённый в редакторе текст тоже не попадёт в сборку.

### 3. Запустите сборку через интерфейс VS Code

Для автоматической сборки на компьютере нужны Node.js и Git. Если VS Code
сообщает, что npm или git не найден, установите их с nodejs.org и git-scm.com
и перезапустите VS Code. Либо используйте ручной способ ниже.

1. Откройте package.json. В scripts должно быть действие:
   `"prepare:release": "node scripts/prepare-release.mjs"`.
   Если его нет, выбрана старая ветка или ещё не перенесён сборщик.
2. В боковой панели «Проводник» найдите раздел “NPM Scripts”. Если он скрыт,
   откройте палитру команд и найдите “NPM: Focus on NPM Scripts View”.
3. Разверните package.json в этом разделе и нажмите значок запуска рядом
   с `prepare:release`.
4. Дождитесь успешного завершения. Внизу появится строка с `directory`,
   `files`, `bytes` и `releaseReady: false`.
5. В проводнике проекта откройте dist. В нём появится НОВАЯ папка вида
   `ReferenceSync-1.2.1-XXXXXX` и файл с таким же именем и окончанием
   `.inventory.json`. Выбирайте путь из результата последнего запуска,
   а не старую папку от предыдущего выпуска.

`releaseReady: false` — намеренная отметка: сборщик проверяет состав файлов,
но не может подтвердить живую работу плагина и прохождение модерации.

Inventory — список файлов, размеров, контрольных сумм и исходного коммита.
Храните его рядом с выпуском. Внутрь папки плагина его переносить не нужно.
После любого изменения чистой папки старый inventory уже не соответствует
её содержимому. Поэтому логотип и код лучше менять в рабочем проекте,
делать коммит и запускать сборку заново.

## Что должно остаться в чистой папке

```text
ReferenceSync-версия-суффикс/
├── manifest.json
├── index.html
├── README.md
├── CHANGELOG.md
├── js/                  программный код
├── styles/              стили
├── assets/              иконки, логотип, курсоры, шрифты и лицензии
└── docs/
    ├── PRIVACY.md
    ├── REVIEW.md
    └── RELEASE.md
```

Точное правило текущего сборщика:

- В js — отслеживаемые Git файлы .js.
- В styles — отслеживаемые Git файлы .css.
- В assets — отслеживаемые Git .svg, .png, .woff2, .otf, .txt и .md.
- В docs — только три перечисленных документа.
- В корне — только manifest.json, index.html, README.md и CHANGELOG.md.

Если в будущей версии появится новый необходимый формат, например .webp
или отдельный файл данных .json, нужно обновить разрешённый список сборщика.
Нельзя считать, что новый ресурс автоматически попадёт в пакет.

Сборщик проверяет основные локальные импорты и ресурсы, наличие лицензий,
формат WOFF2 и отключение devTools. Это не полный антивирус и не проверка
всех динамически вычисляемых путей; запуск готовой папки обязателен.

## Что НЕ переносить в папку для Eagle

- .git, .github, .vscode, .idea, .agents, .codex и другие служебные каталоги;
- Full_design, tests, scripts, node_modules, coverage, test-results;
- dist, release, предыдущие сборки и inventory;
- AGENTS.md, PROJECT.md, STATUS current.md, старые STATUS и HANDOFF;
- package.json, lock-файлы и настройки инструментов разработки: текущий
  плагин не использует их во время работы;
- .env, cookies, пароли, токены, профили браузеров, логи;
- .reference-sync, runtime, staging, личные архивы и скачанные публикации;
- ZIP, .eagleplugin, системные .DS_Store/Thumbs.db и временные файлы.

Не удаляйте это из рабочего репозитория и тем более из личной папки
`.reference-sync`! Речь только о составе отдельной папки для распространения.
Рабочие данные могут быть нужны для восстановления незавершённого импорта.
Лицензии шрифтов из assets/fonts обязательно оставляйте.

## Ручной способ без сборщика

1. Создайте совершенно новую пустую папку, например
   `ReferenceSync-1.2.1-clean`, вне рабочего репозитория.
2. Скопируйте в неё четыре корневых файла из списка выше.
3. Скопируйте js, styles и assets. Проверьте, что внутри нет временных
   файлов, личных данных и типов файлов, не относящихся к плагину.
4. Создайте docs и скопируйте только PRIVACY.md, REVIEW.md, RELEASE.md.
5. Проверьте пути logo и main.url в manifest.json, версии, выключенные
   devTools и наличие шрифтов с лицензиями.
6. Выполните запуск, экспорт и установку по следующему разделу.

Безопаснее собирать из пустой папки, чем копировать весь репозиторий
и пытаться вспомнить, что из него удалить. Ручной способ не выполняет
автоматические проверки сборщика и не создаёт inventory.

## Проверка, экспорт и отправка

1. В Eagle: «Плагин» → «Параметры разработчика…» →
   «Импортировать локальный проект». Выберите НОВУЮ чистую папку,
   где непосредственно лежит manifest.json.
2. Если Eagle уже знает ReferenceSync, убедитесь через пункт открытия папки
   плагина, что проверяете именно новый каталог. Не меняйте id ради обхода
   сообщения о существующем плагине. Сохраните старый проверенный пакет.
3. Откройте плагин. Проверьте логотип, номер версии, языки, кнопки,
   поиск и импорт на небольшой тестовой подборке. Сравните число выбранных
   публикаций, реально добавленных материалов и ошибок; карусель может
   содержать несколько файлов, поэтому эти числа не всегда одинаковы.
4. В панели плагинов нажмите правой кнопкой ReferenceSync →
   «Упаковать плагин» / “Pack Plugin”. Сохраните результат отдельно.
5. Должен появиться файл `.eagleplugin`. Не переименовывайте ZIP в этот формат.
6. Установите полученный файл обычным способом Eagle. Проверьте именно
   установленную версию, включая скачивание, импорт, остановку, восстановление
   и повторный запуск без дублей. Повторите на Windows и macOS.
7. На странице плагина в Plugin Center отправьте новую версию, приложив
   `.eagleplugin`, список изменений, актуальные изображения и сведения для
   модератора. Если предыдущая заявка ещё рассматривается, используйте
   доступное в кабинете действие обновления заявки или дождитесь ответа;
   не создавайте второй плагин с другим id.
8. Сохраните вместе: исходный коммит/ветку, чистую папку, inventory,
   экспортированный пакет, сведения о проверках и номер отправленной версии.

## Короткий повторяемый цикл

Исправления и логотип в рабочей ветке → проверка → новая версия и CHANGELOG
→ коммит → сборка новой чистой папки → запуск в Eagle → Pack Plugin
→ установка полученного пакета → проверка на двух ОС → отправка обновления.

Основа процедуры: официальная документация Eagle
https://developer.eagle.cool/plugin-api/publishing/prepare
https://developer.eagle.cool/plugin-api/publishing/package

Коммит 347548e добавил новый логотип. Следующий aefbaa6 удалил assets/logo.png.
