## M1-T09J - настройка пункта "Искать в выбранных папках"
Нужно сделать данный тумблер рабочим. Мы уже реализовали его в программе на python если не ошибаюсь, можешь свериться с гитхабом https://github.com/Rellese/ReferenceSyncforOpus5
Суть в том: "При включении этого режима ReferenceSync сначала даст список доступных досок, коллекций и разделов. Выберите нужные коллекции и нажмите "Продолжить". После этого выбранный режим поиска будет применён только к содержимому отмеченных коллекций. 

Если режим выключен, поиск выполняется по общему списку всех сохранённых публикаций."

То бишь если включить тумблер то поиска публикаций не будет, сначала программа выдаст коллекции. После пользователь выбирает чекбоксами лишь нужные ему коллекции и нажимает кнопку продолжить внизу, после этого программа ищет только те публикации что находятся в данных коллекциях. И ищет она соответственно режиму поиска, то бишь либо только n колличество, либо только последние либо все ну только в выбранных коллекциях. 
+ в данном режиме публикации будут отображаться по коллекциям как древевидное структура, дизайн данной таблице есть в файле Full_design - https://github.com/Rellese/plugin/tree/main/Full_design
Компонент называется Table with Folders в файле на гитхабе так же есть инструкция к реализации
Бонусом так же надо учитывать соцсеть, например в инсте можно только создавать одну папку и внутри неё посты. На pinterest например можно создавать внутри доски раздел, то бишь внутри папки подпапки и уже в них будут посты, соответсвенно структура древевидная может быть как одноуровневая так и двухуровневая
Просто нужно предусмотреть такой сценарий, он не основной и если не ошибаюсь возможен только в pinterest
Так же в данном сценарии публикации должны в eagle создавать и добавляться в соответствующие папки. То бишь если качаешь одну или несколлько (досок/коллекций, не важно чего) публикации должны в eagle создать соответствующию папку/и (название тоже самое) и добавиться туда

7. JS повторно читает cookies браузера при каждой попытке.

Решение:

Сначала создать обезличенные regression tests, затем отдельно
исправить классификацию и продолжение очереди.

Cookie snapshot переносить отдельной задачей после восстановления
корректной обработки ошибок.

## M1-T07M — модель массового изменения чекбоксов

Статус:

`planned`

### Протягивание

1. Нажатие на выключенный чекбокс запускает режим включения.
2. Нажатие на включённый чекбокс запускает режим выключения.
3. Пока кнопка удерживается, затронутые чекбоксы получают выбранное состояние.
4. Повторное прохождение по одному чекбоксу в рамках одного жеста не должно
   переключать его повторно.
5. После `pointerup`, `pointercancel` или потери окна жест завершается.
6. Обычный одиночный клик продолжает работать.
7. Управление через Space и Enter продолжает работать.
8. Disabled и уже импортированные элементы не изменяются.

### Shift-click

1. Обычный клик по чекбоксу устанавливает якорь диапазона.
2. Пользователь может прокрутить список после установки якоря.
3. Shift-click по другому чекбоксу изменяет весь диапазон между якорем
   и вторым чекбоксом, включая оба крайних элемента.
4. Если второй чекбокс включается, весь диапазон включается.
5. Если второй чекбокс выключается, весь диапазон выключается.
6. Диапазон определяется по текущему визуальному порядку строк.
7. Скрытые текущими фильтрами публикации не изменяются.
8. Disabled и уже импортированные элементы пропускаются.
9. Якорь сохраняется при обычной прокрутке.
10. Обычный клик без Shift устанавливает новый якорь.
11. Новый поиск или полная перерисовка списка сбрасывает старый якорь.
12. Закрытие модального окна сбрасывает его локальный якорь.

### Синхронизация состояния

После протягивания или Shift-click должны корректно обновляться:

- набор выбранных публикаций;
- `post.selectedComponents`;
- счётчик выбранных файлов;
- родительский чекбокс;
- состояния `on`, `off` и `mixed`;
- фактический список элементов, передаваемый в импорт.

# Решение по удалению элементов и нумерации

Дополнительные задачи по моделированию массового удаления элементов Eagle
не выполняются.

Не планируются:

- отдельная проверка нумерации после массовых ручных удалений;
- сценарий `1000 элементов → удалено 250`;
- полный постоянный реестр `номер → Eagle item ID`;
- автоматическое восстановление последовательности после произвольного
  массового удаления старых элементов.

При массовом ручном удалении пользователь при необходимости самостоятельно
корректирует начальный номер перед следующим импортом.

Это принятое ограничение текущей версии, а не незавершённая задача.

# Обновление 2026-08-28 — M1-T05B: оптимизация cookies и производительности

Статус:

`in progress — cookie snapshot реализован и проверен; сравнение режимов скорости ещё не выполнено`

Проверенные production-коммиты:

- `8621712b627603b59f769011463f919a3989d5d8` — проверка Instagram-аккаунта использует созданный cookie snapshot;
- `51a0ef0eff9bb07aee11c219fca25f7560efc5c5` — один cookie snapshot используется для проверки аккаунта и Saved discovery;
- `2c08e4774b28b36c4d4e8d5b0527dba348c1feb9` — один cookie snapshot используется для всей очереди скачивания.

Реализовано:

1. Cookies браузера больше не читаются повторно между проверкой аккаунта и Saved discovery.
2. Discovery получает временный cookie-файл через `--cookies`.
3. Для очереди скачивания создаётся один отдельный cookie snapshot.
4. Все публикации одной очереди используют общий snapshot через `--cookies`.
5. Временные cookie-файлы удаляются после завершения, ошибки или остановки операции.
6. Старый путь через `--cookies-from-browser` сохранён там, где создаётся snapshot.
7. Размер предыдущего поиска не оказывает заметного влияния на скорость импорта.

Baseline поиска до оптимизации:

- 10 публикаций — 32 секунды;
- 50 публикаций — 40 секунд;
- 200 публикаций — 59 секунд.

Поиск после повторного использования cookie snapshot:

- 10 публикаций — 14 секунд;
- 50 публикаций — 19 секунд;
- 200 публикаций — 46 секунд.

Итоговое ускорение поиска:

- 10 публикаций — на 18 секунд, примерно 56%;
- 50 публикаций — на 21 секунду, примерно 53%;
- 200 публикаций — на 13 секунд, примерно 22%.

Контрольный baseline импорта до общего snapshot очереди:

- 1 публикация — 12–13 секунд;
- 3 публикации — 35–36 секунд.

Импорт после общего snapshot очереди:

- 1 публикация — 12–13 секунд;
- 3 публикации — 21–23 секунды.

Итог импорта:

- одиночный импорт не замедлился;
- импорт трёх публикаций ускорился примерно на 36–42%;
- среднее время трёх публикаций сократилось примерно с 35,7 до 21,7 секунды;
- преимущество увеличивается при росте количества публикаций.

Живая проверка:

- плагин открывается в Eagle;
- поиск работает;
- импорт одной публикации работает;
- импорт трёх публикаций работает;
- результаты не зависят существенно от предыдущего лимита поиска;
- GitHub Actions для production-коммита `2c08e477` завершился успешно.

Не завершено:

1. Safe, Balanced и Lightning не сравнены одинаковыми повторными измерениями.
