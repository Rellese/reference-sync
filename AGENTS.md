# AGENTS.md — правила работы над ReferenceSync

Этот файл обязателен для чтения перед любыми изменениями проекта.

Если работа продолжается в новом чате или другим исполнителем:

1. Прочитать `AGENTS.md`.
2. Прочитать `PROJECT.md`.
3. Прочитать `STATUS.md`.
4. Проверить актуальный код репозитория.
5. Продолжить только задачу, указанную в `STATUS.md`.
6. Не начинать следующую задачу, пока не выполнены критерии текущей.

---

# 1. Цель проекта

ReferenceSync — компактный плагин Eagle для переноса сохранённых публикаций из социальных сетей в Eagle.

Главные требования:

- простой сценарий установки;
- минимум действий пользователя;
- стабильная работа Instagram;
- дизайн 1:1 с предоставленными макетами;
- отсутствие дубликатов;
- восстановление после остановки или ошибки;
- возможность добавлять новые социальные сети модулями;
- соответствие требованиям модерации Eagle Plugin Center;
- чистый, понятный и поддерживаемый код.

Владелец проекта — дизайнер и не обязан разбираться в коде, терминале или Git.

Все инструкции владельцу должны быть:

- написаны простым языком;
- разбиты на короткие шаги;
- содержать точные названия кнопок и файлов;
- не предполагать знание программирования;
- не использовать терминал, если задачу можно выполнить через интерфейс.
- по умолчанию использовать интерфейс VS Code для редактирования,
  коммитов и синхронизации;
- использовать браузерный редактор GitHub только как запасной вариант;
- не предлагать терминал, если действие можно выполнить через VS Code.

Репозиторий:

`https://github.com/Rellese/ReferenceSyncforOpus5`

# 3. Архитектурные правила

Production-плагин должен оставаться компактным.

Основная архитектура:

- HTML/CSS — интерфейс;
- JavaScript — состояние, бизнес-логика и интеграция с Eagle;
- source adapters — отдельные модули социальных сетей;
- gallery-dl — изолированный движок получения данных;
- локальное хранилище — только необходимые настройки, задания и идентификаторы импортированных публикаций.

Полное Python-приложение, PyQt GUI и старые служебные Python-файлы не включаются в production-плагин.

`gallery-dl` запускается только во время поиска или скачивания и не должен постоянно работать в фоне.

Каждая социальная сеть должна подключаться через единый контракт:

- `discover`;
- `normalize`;
- `download`;
- `validate`.

Instagram реализуется первым.

Остальные источники нельзя считать рабочими без живого тестирования.

# 4. Правила компактности

Ориентиры, а не автоматические запреты:

- один обычный JS-файл — желательно до 250–350 строк;
- файл больше 500 строк требует обоснования или разбиения;
- одна функция — желательно до 40–60 строк;
- один модуль должен иметь одну понятную ответственность;
- одинаковая логика не должна дублироваться;
- нельзя создавать абстракции без реальной текущей необходимости.

Не допускаются:

- огромные универсальные файлы;
- дубли старых и новых реализаций;
- временные patch-файлы;
- код «на будущее», который нигде не используется;
- неподключённые skeleton-модули;
- комментарии, утверждающие, что функция работает, если она не проверена;
- массовые изменения нескольких подсистем в одной задаче.

Если новый код заменяет старый, старый код удаляется после прохождения проверок.

# 5. Правила выполнения задач

Перед изменением кода исполнитель должен указать:

- ID текущей задачи;
- цель;
- какие файлы планируется изменить;
- что не входит в задачу;
- как будет проверен результат.

Одна задача должна решать одну проблему.

Нельзя в одной задаче одновременно:

- исправлять Instagram;
- менять дизайн;
- добавлять новую социальную сеть;
- проводить глобальный рефакторинг;
- переписывать документацию всего проекта.

После выполнения задачи необходимо:

1. проверить изменённую функцию;
2. проверить, что плагин запускается;
3. убедиться, что нет лишних файлов;
4. обновить `STATUS.md`;
5. сделать один понятный коммит.

Формат названия коммита:

`M<этап>-T<задача>: краткое описание`

Пример:

`M1-T03: normalize Instagram carousel components`

---

# 6. Запрет на неподтверждённые заявления

Нельзя писать «работает», если функция не проверена.

Используются статусы:

- `implemented` — код написан, но не проверен в реальном окружении;
- `fixture-tested` — проверено на сохранённых тестовых данных;
- `live-tested` — проверено в Eagle с реальным источником;
- `release-ready` — пройдены все критерии и проверена release-сборка;
- `blocked` — работа остановлена из-за известной причины;
- `not-implemented` — функция отсутствует.

Instagram считается рабочим только после живого тестирования.

# 7. Тестирование

При переносе логики из Python:

1. получить обезличенный пример входных данных;
2. зафиксировать ожидаемый результат;
3. написать или исправить JS-реализацию;
4. сравнить результат с Python;
5. проверить реальный сценарий в Eagle.

Обязательные Instagram-сценарии:

- одиночное изображение;
- видео/Reel;
- карусель изображений;
- смешанная карусель;
- публикация без описания;
- несколько коллекций;
- только новые публикации;
- полный поиск;
- последние N публикаций;
- остановка операции;
- повторный запуск;
- частично завершённый импорт;
- защита от дубликатов;
- импорт в выбранную папку Eagle;
- ошибка cookies;
- ошибка соединения;
- rate limit.

Секретные данные, cookies и токены нельзя добавлять в Git.

# 8. Чистота репозитория

В Git нельзя добавлять:

- cookies;
- пароли;
- токены;
- данные аккаунтов;
- скачанные публикации;
- пользовательские архивы;
- runtime Python;
- временные staging-файлы;
- логи;
- release ZIP;
- системные файлы;
- файлы редакторов;
- временные отчёты ассистентов;
- вложенные архивы без необходимости.

Перед каждым коммитом необходимо проверить список изменённых файлов.

---

# 9. Требования модерации Eagle

Плагин должен быть подготовлен к модерации Eagle Plugin Center.

Обязательно:

- точное описание реально работающих функций;
- раскрытие зависимости от gallery-dl;
- объяснение использования cookies браузера;
- отсутствие скрытой передачи данных;
- отсутствие сохранения cookies плагином;
- понятное согласие перед установкой внешней зависимости;
- отсутствие скрытых установок и обновлений;
- корректная отмена длительных операций;
- понятные ошибки;
- отсутствие зависаний интерфейса;
- безопасная работа с пользовательскими файлами;
- чистая release-сборка;
- инструкции для модератора;
- проверка Windows и macOS;
- использование официального Eagle Plugin API там, где это возможно.

Нельзя публиковать функции, которые присутствуют только в виде skeleton-кода.

Если для релиза готов только Instagram, описание релиза должно говорить только о рабочем Instagram.

# 10. Работа с владельцем проекта

Владелец проекта не должен вручную редактировать программный код без точной инструкции.

Если требуется действие владельца, необходимо написать:

1. какую страницу или программу открыть;
2. какую кнопку нажать;
3. какой файл выбрать;
4. какой текст вставить;
5. что должно появиться в результате;
6. что прислать для проверки.

Нельзя писать владельцу только:

- «запусти тесты»;
- «сделай commit»;
- «открой терминал»;
- «исправь конфликт»;
- «проверь PATH».

Каждая такая инструкция должна быть расшифрована пошагово.

Пароли, cookies и личные архивы у владельца не запрашиваются.

---

# 11. Порядок этапов

Работа выполняется в следующем порядке:

- M0 — документация, порядок и фиксация baseline;
- M1 — стабильное ядро Instagram;
- M2 — импорт и интеграция с Eagle;
- M3 — дизайн 1:1;
- M4 — простая установка и подготовка движка;
- M5 — тестирование и подготовка к модерации;
- M6 — добавление остальных социальных сетей;
- M7 — Meta Archive и дополнительные функции;
- M8 — локализации.

Нельзя переходить к следующему этапу только потому, что текущий кажется сложным.

---

# 12. Завершение рабочего сеанса

Перед окончанием работы исполнитель обязан обновить `STATUS.md`.

В нём должны быть указаны:

- последний проверенный commit SHA;
- текущий этап;
- выполненная задача;
- следующая задача;
- что было проверено;
- что не было проверено;
- известные ошибки;
- точное следующее действие.

GitHub и эти документы являются памятью проекта.

История чатов не является источником истины.
